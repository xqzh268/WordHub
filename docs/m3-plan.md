# 下一步开发计划：M3 协调器与群聊

**日期：2026-10-04**　依据：[m2-1-acceptance.md](m2-1-acceptance.md)（遗留项 R1–R9）；上位文档 [p1-plan.md](p1-plan.md)、[research/multi-agent-orchestration.md](research/multi-agent-orchestration.md)。

M3 把“一个 Agent 一次回复”升级为“一组 Agent 完成一件事”：任务图、质询、写入串行化、可恢复的审批与中断、费用预估。预计 **约 13 个工作日**（含 M3.0 的 1.5 天）。

## 一、现状与起点

| 已具备 | 缺口 |
|---|---|
| 单 Agent 运行：AGENT.md、模型解析、工具、权限、审批、用量、上下文清单（真实模型 20/20） | 没有任务图；运行之间互不知晓 |
| 事件日志、投影、受控写盘、外部修改保护、中断清扫 | 库里没有任务表（`Task` 契约已有，未落库） |
| 界面：群聊、审批卡、质询线程卡、时间线 | 质询线程卡只有演示数据；没有任务进度展示 |
| Pi 的消息上下文是普通 JSON，可直接落库 | 审批与中断的运行**无法跨重启继续**，只能“过期” |
| 默认入口是纲领，Agent 之间不能互相提问 | 没有 `challenge / question` 协议与轮次限制 |

**结构性前提**：worker 已有 1259 行，且 fallback 等编排逻辑因此无法单测。**M3 的协调器全部建在 `packages/runtime`，worker 只做消息路由。** 这是 M3.0 的第一件事。

## 二、已定的产品决策如何落地

| 决策 | M3 中的体现 |
|---|---|
| 默认“单写手 + 按需评审”，全员流水线为显式选项，运行前显示预估费用 | “写一章”的默认工作流是 **写手 → 编辑**；评审在用户点“请评审”或定稿时才运行；“全流程”（写手 → 编辑 → 评审 → 返工）是显式开关，开启前显示预估费用 |
| 自建 Agent 可以写正文 | 写入串行化与 `parentRevision` 检查对所有 Agent 一视同仁 |
| 质询有界（≤2 轮），超限升级给用户 | 协调器计数；第 3 轮前强制升级为裁决卡 |

## 三、工作拆分

### M3.0 遗留项与结构整理（1.5 天，先做）

| 事项 | 对应 | 验收 |
|---|---|---|
| 把 worker 里的运行编排迁入 `packages/runtime`（`RunExecutor`：模型选择 → fallback → 工具 → 审批 → 收尾），worker 缩到只做消息路由（目标 < 300 行） | R3 | 现有 20/20 与 11/11 保持通过 |
| fallback 的故障注入测试：faux provider 让主模型返回错误，断言发出 `run.fallback` 且备用模型产出结果 | R3 | 新增 faux 测试 |
| 审批卡显示**路径、字数、相对当前文件的差异统计**，可展开完整差异 | R1 | 修正断言 C2：检查真实路径文本 |
| 权限被拒时在群聊里加确定性提示条（“权限被拒：路径不在写入范围内”），不依赖模型转述 | R2 | 新增断言检查该元素 |
| “测试连接”发真实的最小请求；环境变量密钥与保存的密钥状态一致 | R4 | 填错的密钥显示失败 |
| 过期卡措辞与“重新发起”按钮；重载后工具标签保持中文 | R5 | 点击后以原提示词重新发起 |
| 切换模型时保持当前思考强度（不支持则取推荐值，而非 `off`） | R6 | 单测 |
| 夜间回归缺密钥时显式失败或标记跳过；收紧 B3、E2 断言 | R7、R8 | 缺密钥时工作流不显示绿色 |

### M3.1 任务引擎（2 天）

- **存储**：新增迁移 `tasks` 表，字段对齐 [task.schema.json](../packages/contracts/src/schema/task.schema.json)（`status / dependencies / assignedAgent / contextSnapshotId / attempt / budget / checkpoint`）。
- **事件**：`task.created / ready / started / succeeded / failed / cancelled / waiting_approval`，任务状态是事件的投影，可重放。
- **协调器**（纯逻辑，`packages/runtime/coordinator`）：给定任务图与事件，输出下一步该调度的任务；并发度可配置（默认 2）；失败重试遵守 `maxAttempts`。
- **验收**：属性测试——随机 DAG 与随机成败序列，协调器不会调度依赖未满足的任务、不会重复调度、终态一致。

### M3.2 声明式工作流与路由（1.5 天）

- 工作流定义放在 `packages/novel/workflows/*.json`（节点、依赖、Agent、输入输出引用、条件边）。首批：
  - `write-chapter`：写手 → 编辑；
  - `write-chapter-full`：写手 → 编辑 → 评审 →（有阻塞质询）返工，最多 2 轮；
  - `review-only`：评审单独对已有章节核验。
- **路由**：`@agent` 直投（沿用现状）；`@all` 并行扇出，由纲领汇总；未 `@` 时先按规则匹配（含“写第三章”这类意图关键词），无法判断才交纲领。
- **验收**：faux provider 脚本化三条工作流，断言任务顺序、产物传递与终态。

### M3.3 质询与提问协议（2 天）

- 工具：`challenge.raise`（目标产物、段落范围、证据引用、严重度）、`challenge.reply`（接受 / 反驳 / 部分接受、补丁引用）、`question.ask`。
- 协调器计数：同一线程最多 2 轮；第 2 轮仍反驳 → 生成 `escalation`，工作流暂停等用户裁决；`blocking` 级质询未解决，下游任务不得进入成功态。
- 投影出**真实的质询线程卡**（现在只有演示数据），裁决卡的选择写成事件并驱动工作流继续。
- **验收**：用《长安夜》样例（见下）里预埋的“左撇子 / 右手按刀”矛盾，faux 脚本化“评审提出质询 → 写手反驳 → 评审维持 → 升级裁决”，全链路事件与界面一致。

### M3.4 可恢复的审批与中断运行（2 天）

- 在两个时机把 Pi 的消息数组落库（`run_snapshots` 表，**不进事件日志**）：进入 `waiting_approval` 时、每个回合结束时。存：消息、系统提示、模型引用、待执行的工具调用（名称、参数、`toolCallId`）。
- **审批跨重启**：重开后审批卡依然有效；批准则按保存的参数执行工具，把结果写回快照消息，重建 Agent 继续；拒绝同现状。
- **继续被中断的运行**：中断的运行显示“继续”，从最近的回合快照恢复。
- 取代 M2.1 的“已过期，可重新发起”。
- **验收**：`m2-live-e2e` 场景 E 改为“强杀重开后点批准，文件落盘且运行正常收尾”；另加 faux 测试覆盖快照往返。

### M3.5 写入串行化（1 天）

- 协调器按产物加锁；任务启动时记录 `parentRevision`，提交时若已变化：自动基于最新版本重试（≤1 次），仍冲突则降级为提案并提示。
- 与 M1.1 的“磁盘哈希守卫”协同：外部修改与 Agent 并发写入走同一条冲突路径。
- **验收**：faux 脚本让两个 Agent 同时写同一章，结果是一个成功、一个重试或降级，**不丢任何一方的内容**。

### M3.6 费用预估与预算（1 天）

- 运行前预估：每个任务的输入 token（取上下文清单的估算）+ 输出 token（取该 Agent 在 `usage` 表里的历史均值，缺省用保守常数）× 模型单价。
- 工作流启动前弹出“预估费用”确认卡；显式开启全流程时必须确认。
- **费用**：运行前给出项目流程预估，运行中显示实际用量；按最新决定，单次运行不设预算上限。
- **验收**：预估与实际花费的偏差记录在回归结果里，作为后续校准依据。

### M3.7 群聊界面（2 天）

- 任务进度时间线（○ 待办 / ◐ 进行中 / ● 完成 / ✕ 失败），并行任务用泳道或堆叠印章。
- 真实的质询线程卡、裁决卡、预估费用卡、“继续”与“请评审”按钮。
- 会话级用量汇总。
- **验收**：Playwright 驱动整条 `write-chapter-full` 流程，截图入 [design/](design/README.md)。

### M3.8 集成回归（1.5 天）

- **样例项目《长安夜》**：把演示稿做成 `examples/长安夜/`（章节、设定集含“裴照是左撇子”、一处预埋矛盾）。**这些设定均是我随手编的虚构内容，不当作你的创作**；若你要扩写人物与情节，我会先问你的想法。
- 真实模型回归新增场景：写第三章（写手 → 编辑）→ 请评审 → 评审应找出预埋矛盾 → 质询线程 → 裁决 → 返工。
- 夜间回归纳入新场景；faux 工作流测试纳入 CI。

## 四、M3 总体验收

1. `write-chapter`：用户一句话 → 写手写章节 → 编辑改写 → 落盘，群聊里能看到任务进度与各自的用量。
2. 点“请评审”：评审在《长安夜》里找出预埋矛盾，发起质询；写手应答；第 2 轮仍分歧时出现裁决卡，裁决后工作流继续。
3. 审批中强杀应用，重开后点“批准”，文件落盘、运行收尾；被中断的运行可一键继续。
4. 两个 Agent 并发写同一章，不丢内容。
5. 全流程开启前显示预估费用；运行中显示实际用量，运行不因费用自动暂停。
6. 真实模型回归与 faux 工作流测试均通过，CI 绿。

| 单次运行预算上限 | 不设上限 | — |

## 六、风险

| 风险 | 缓解 |
|---|---|
| 协调器与 worker 重构同时进行，回归面大 | M3.0 先做“行为不变”的迁移，靠 20/20 与 11/11 兜底，再加新能力 |
| Pi 消息快照在跨版本后不兼容 | 快照带版本号；Pi 锁定 `1.0.0`；恢复失败时降级为“重新发起” |
| 评审“走过场”或过度质询 | 用预埋矛盾做检出率基准，同时放入一章无矛盾文本测误报率 |
| 多 Agent 费用失控 | 默认不开全流程；预估与用量按任务汇总可见 |
| 质询陷入循环 | 协调器硬性 ≤2 轮，第 3 轮必须升级给用户 |

## 七、之后

M4 小说流程（约 2 周）：纲领分层问答与设定集生成、编辑 / 评审清单（ConStory 分类）、观察者抽取候选事实。M5 编辑器与收尾（约 1.5 周）：ProseMirror 纸面编辑、DOCX/TXT 导出、自建 Agent 表单、Mica 与命令面板、打包。
