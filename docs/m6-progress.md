# M6 参考库与图谱进展

更新日期：2026-11-04。范围与路线见 [m6-plan.md](m6-plan.md)。**M6.1（参考库底座）与 M6.1b（书架形态）已完成；M6.2（图谱）、M6.3（文献能力）未开始。**

## M6.1：参考库底座（已实现）

侧栏"参考库"：导入资料 → 本地解析成按章文本 → 阅读 → 全文检索 → 选段（提问 / 作为文风示范 / 复制引用）→ Agent 可用工具查阅。需要先链接写作文件夹。

**存放**：`<项目>/.wordhub/references/<ref-xxxxxxxxxxxx>/`，内含原件副本 `source.<ext>`、`reference.json`（含 `schemaVersion`）、按章 `text/0001.txt…`。id 取原件 sha256 前 12 位，同一文件重复导入得到同一本，不重复入库；导入先写临时目录再改名，失败不留半本书；目录链上有符号链接就拒绝。文件路径只来自系统对话框。

**格式**

| 格式 | 解析 | 拒绝 / 局限 |
|---|---|---|
| TXT、Markdown | 严格 UTF-8 → 回退 GB18030；识别 BOM、UTF-16；按"第N章/回/节、楔子、序章、后记、番外、Chapter N"切章，没有章标题按约 8000 字在段落边界分块 | — |
| EPUB | jszip 读 OPF/spine，目录取 EPUB3 nav 或 EPUB2 ncx，jsdom 取正文；源文件硬折行的中文接成整段 | **DRM 加密的明确拒绝**（只允许字体混淆）；不去 DRM |
| DOCX | 读 `document.xml`，用标题样式（Heading/标题 N）分章，没有就按章标题文字 | 旧版 .doc 提示另存为 .docx |
| PDF | pdf.js 取文字层，按章标题或每 10 页聚合 | **没有文字层（扫描件）明确拒绝，不做 OCR**；加密 PDF 拒绝 |
| MOBI / AZW3 | **不支持**，提示先用 Calibre 转 EPUB | — |

安全上限：原件 ≤ 200 MB，正文 ≤ 3000 万字，章节 ≤ 5000，压缩包条目 ≤ 2 万且解压总量 ≤ 500 MB（防 zip 炸弹），PDF ≤ 3000 页。元数据清洗：PDF 里的网页地址、"Microsoft Word - x.docx"、"Untitled"不当书名；"Un-named"、"Administrator"之类占位作者当作没有。

**阅读与检索**：整章阅读（界面不受 Agent 的单次 2 万字上限约束）；全文检索不区分大小写，可限定当前这本，命中点击跳到章节并高亮检索词，最多 100 条。

**选段与锚点**：选中文字出现操作条——"提问"把引文和出处（《书名》章名）带进工作台输入框；"作为文风示范"；"复制引用"。选区换算成整章文本里的 `[start,end)`，服务端用原文重新切片，不信任客户端传来的引文；用时校验引文与原文逐字一致。

**文风示范**（兑现 10-22 的决定）：写入 `.wordhub/bible/style-samples.md`，走受控写盘（记为用户修订，可撤销，带内容哈希基线防覆盖）；每段 20–600 字、最多 5 段、重复拒绝；每条带出处和可回查的锚点（`ref-…/0003/120-480`），文件里的引文逐行加 `> ` 前缀，所以引文里出现"## 示例"也不会被当成新条目。会写正文的 Agent 和纲领的上下文在"文风基准"之后多一层"文风示范"，并带"只学笔法与节奏，不得照抄情节与原句"的说明；只读的评审不收到。

**Agent 工具**：`reference.list`、`reference.search`、`reference.read`，只读。Agent 要声明工具，并且 `memoryScopes.read` 含 `references`，缺一个就被权限层拒绝。内置写手和纲领已开通（提示词要求只在作者要求参考或需要对照文风时才查，不得照抄，正文里不提参考书）；自建 Agent 表单里有"查阅参考库"勾选（自动带上读取范围）。

**隐私**：资料只保存在项目文件夹里；界面明说"向 Agent 提问时，所选文字会发给你配置的模型服务商"。

### 开发中发现并修复的问题

1. **Electron 的 utilityProcess 里 pdf.js 不工作**：`process.type` 为 "utility"，pdf.js 不把它当 Node，要求 `DOMMatrix` 和 worker。单测在普通 Node 里全过，到 Electron 里才暴露。已补最小 `DOMMatrix` 占位并指定 worker 文件（只取文字、不渲染）。
2. PDF 元数据标题是垃圾（Chromium 打印的 PDF 标题是页面网址）。已清洗。
3. docx 库默认的作者 "Un-named" 被当成真作者显示。已清洗。
4. 回归脚本 `m2-live-e2e` 里"设定集注入层"的夹具已过时（M4.2 之后不再注入 `bible.md`），一并修正。
5. 回归与 CI 里发现：应用运行中新增的 AGENT.md 要重启才认；现已在 `@` 未知名字时自动刷新、窗口聚焦时刷新。
6. 一次 CI 的 paper e2e 步骤挂起半小时以上：所有 e2e 脚本改用限时关闭应用，CI 加了步骤和整体超时。

### 未验证 / 局限

- 真实模型每项只跑 1 次、只用 flash；没有测很长的书（几十万字）的导入耗时与检索性能，也没测 PDF 很大时的内存。
- pdf.js 目前跑在"假 worker"里，大 PDF 会占用后台进程的 CPU；中文以外的 PDF（双栏、公式、竖排）没测，双栏论文的行序会乱。
- 章节切分是启发式的：非常规章标题（"一、"、纯数字、卷中卷）会切成按段落分块；没有手动调整章节的功能。
- 打包后（asar）`pdfjs-dist` 的 worker 路径还没验证，留给 alpha 打包阶段。
- MOBI 不支持，DRM 与扫描件只是明确拒绝。

## M6.1b：书架形态（已实现）

参考库从"列表 + 阅读"升级为书架（用户 2026-11-04 提出，要为论文/基金/办公材料打底）。

- **书架**：封面网格 ⇄ 列表；封面取 EPUB 自带封面，没有就生成文字封面（底色由 id 稳定派生）；PDF 首页封面留给 M6.3。左栏：全部 / 收藏 / 在读·未读·读完（带计数）/ 可能重复 / 集合 / 标签。
- **整理**：收藏；标签（≤20 个、≤30 字、大小写不重复）；**集合**（类似文件夹，一本书可同属多个，可新建/重命名/删除，删集合不删书）；阅读状态（打开即自动"在读"，可手动改）与按章节算的进度条。
- **筛选与排序**：筛选框按书名/作者/标签/出版方/DOI/ISBN/备注；排序：最近导入、最近阅读、书名、作者、年份（缺值排最后）。
- **元数据编辑**：书名、作者、年份、类型（小说/论文/报告/资料/其他）、出版方、DOI（格式校验）、ISBN、备注；校验失败给明确错误且不保存。
- **重复检测**：书名与作者归一化后相同的不同文件，导入时提示"可能是同一本书的另一个版本"，并在"可能重复"分类里成组列出；不自动合并。
- **批注与高亮**：四色高亮 + 笔记（≤2000 字），引文由后台按区间从原文切出；右侧批注面板可改色、改笔记、删除；存 `annotations.json`。
- **存储**：`reference.json` 升到 `schemaVersion 2`（只增字段，旧版可读）；集合在 `.wordhub/references/library.json`；封面 `cover.<ext>`；库级读改写走按目录的串行锁，写入先临时文件再改名。
- **Agent**：`reference.list` 的输出多了类型、年份、标签、状态、收藏。

## M6.2a：关系图谱（已实现）

用户 2026-11-04 明确要求图谱不只是展示：要能点节点看详情、以人物身份接受采访、按整个图谱推演走向（参考 MiroFish 的思路，该项目是 AGPL-3.0，我们只借鉴思路、不拷贝代码）。因此 M6.2 拆成三步：a 图谱视图（本节），b 人物采访，c 推演。b、c 见后文。

- **数据**：事实新增种类 `relation`（人物关系）：`subject → object` + 关系名 `relation` + 逐字原文锚点。`fact.propose` 校验：关系必须同时有 object 与 relation、两端不能是同一人、锚点必须逐字出现在章节里；别的种类多给的 object/relation 不入库。史官提示词同步：只记正文明确写到或明确变化的关系，关系变化就新记一条，不要改旧的；同场出现不算关系。已确认的关系进入写手/评审的“已确认事实”上下文（`裴照 →同伴→ 苏晚`）。
- **图谱是投影**：`projectGraph` 从已确认的人物状态与关系事实算出节点和边，不另存一份可手改的图。出现时刻 = 事实所在章节在时间轴上的位置（按章号排序，"第十章"在"第二章"之后）。已确认才画；待确认可勾选“显示待确认”以虚线淡色显示；已驳回永不出现。同一对人物的关系取最新一条，变化过程在边的详情里按章节先后列出。
- **视图**：自绘 SVG + HTML 节点（没有引入 React Flow）。理由：节点是原生按钮，键盘/读屏/测试都直接可用；确定性力导向布局（按“全部章节”算一次，拖时间滑块时节点不乱跳）；无新依赖。滚轮缩放、拖动平移、适应窗口。章节时间滑块：拖到更早的章节，后来才出现的人物、关系和状态都消失（防剧透）。节点详情：首次出现、截至当前的状态、关系（点人名可切换）、每条事实的原文出处，并能跳回工作区对应章节。
- **事实页**：关系事实显示为“A →关系→ B”。

### M6.2a 局限

- 没有别名合并（“黑衣人=萧某”这类带揭示时刻的别名）：同一人的不同称呼会成两个节点。
- 节点来自人物状态与关系事实；没有地点/组织/物件节点。
- 真实模型只跑 1 次、只测一个短样章；长篇的人物花名册、跨章共指没有测。
- 图只展示“截至某章”的状态，不区分故事内时间与叙事揭示时间（倒叙、悬疑反转会不准）。

## M6.2b：人物采访（已实现）

点图上的人物 → 详情栏切到“采访”，以他的身份回答作者的提问。

- **知识边界（硬过滤）**：模型只看到截至所选章节、**已确认**、与这个人物有关的事实（他的人物状态与关系、他在其中出现的关键事件、身边人在他亲历的章节里的状态变化），以及这些章节的摘要、`characters.md` 里他那一节、`setting.md`。后文、待确认、已驳回的事实、别人的事件、术语都不进提示词。拖时间滑块换章节就是**另一场采访**，各自保存对话。
- **回答要带依据**：提示词要求用到某条事实就标 `[F#]`；界面把标注变成上标序号，下方列出对应章节、陈述与原文；没有对应事实的标注会被警告；既没依据又不承认“不知道”的回答会提示“请谨慎采信”。
- **事后越界检查**：回答里出现起点章节之后才登场的人物名，直接标红警告并说明他在第几章才出现。
- **两种模式**：采访（人物口吻，不出戏）、作者（分析动机，第三人称）；两者知识边界相同。
- **保存对话**：存成 `.wordhub/graph/interviews/<时间>-<人物>-<章节>.md`（标明非正文、不改设定），文件名里的路径字符会被清掉。
- **模型**：用写手的模型设置（单轮生成，不是对话式 run，不进聊天记录，也不计入运行预算；界面显示本次 token 用量）。

## M6.2c：推演（已实现）

工具栏“推演”：选起点章节（时间滑块）、2–6 个人物、可选的“假如……”（≤500 字）、轮数（1–6）→ 先显示估算（调用次数、输入/输出 token 量级）→ 开始。参考了 MiroFish 的“多智能体模拟 + 报告”思路，但不照搬：规模小、可控、可审计、对着已确认的事实图谱。

- **逐步推演**：界面按“轮 × 人物”逐步调用（无状态的单步接口），所以能显示进度、随时停止、出错时保留已有记录并可“用已有记录生成报告”。每个人物看到自己的已知事实 + 起始局面 + 其他人**公开**的行动，**看不到别人的心思**；输出格式固定为【行动】【心思】。心思默认折叠，标明“只有他自己知道”，只有最后的报告能看到。
- **推演报告**：推演小结、可能的走向（2–3 种，标“较大/中等/较小”）、关键转折点、与既有设定的冲突或存疑之处、对后续章节的建议；明确是推演不是预言。
- **非正史**：结果只存为 `.wordhub/graph/branches/<时间>-<假如>-<章节>.md`，页首标“非正史”；**不写章节、设定或事实**（e2e 校验章节文件逐字不变）。
- **上限**：≤6 人、≤6 轮、≤36 步；记录条目 ≤2000 字；开始前显示估算，用户点“开始推演”才跑。

### M6.2b/c 局限（如实）

- **知识边界是启发式的**：“他知道什么”用“有他的事实的章节”近似亲历，没有 `knows(角色, 事实)` 认知边；不在场却通过别人得知的事、角色间的误会与隐瞒都表达不了。`characters.md` 里作者写的未揭晓设定会进提示词（提示词要求不主动透露，但模型不一定遵守）。
- **模型会自由发挥**：真实测试里回答出现了“三年只教出个缩在师父身后的徒弟”这类事实里没有的修饰，没有标“（推测）”。依据序号与越界检查只能抓住引用和人名，抓不住所有编造；回答是素材，不是设定。
- **推演不是预测**：只有 flash 跑过 1 次，没有评估走向的“准确率”（也无从评估）；推演里所有行动对其他人公开、每轮人物顺序固定、没有环境/旁白角色、没有地点与时间推进，规模只有 ≤6 人 × ≤6 轮，远不是 MiroFish 那种成千上万智能体的涌现。长篇、人物很多时，上下文会很长。
- **停止按钮**在 e2e 里没测（mock 太快，无法稳定点到）；出错后“用已有记录生成报告”也只有单测级别的覆盖。
- 采访与推演走“写手”的模型配置，费用不进运行预算和聊天记录；没有单独的每功能模型设置。
- 采访只有单人，没有“多人圆桌”；没有“节点知道什么”的可视化。

## M6.2d：认知边与别名合并（已实现）

用户 2026-11-08 要求先补这两项，解决 M6.2b 的头号局限（“他知道什么”只是按章节近似）。

### 认知边 `knows(人物, 事实, since)`

- **默认推断**（和之前一样，现在集中在一处 `characterKnowledge`，界面、采访、推演共用）：他本人的人物状态与关系、他在场的关键事件、身边人（有直接关系的人）在他亲历章节里的状态变化。只涉及已确认、不晚于所选章节的事实。
- **作者逐条覆盖**：图谱详情栏新增“认知”页签，列出到所选章节为止“他知道（N）”和“读者知道，他不知道（M）”。可以“让他知道（自当前章节起）”、“设为他不知道”、“恢复默认”。起知章节没到时他仍不知道（拖回更早的章节，这条会回到“不知道”）。这样能表达戏剧反讽（读者知道、他不知道）和“人物私下知道、读者后来才知道”。
- **事件溯源**：`knowledge.set` / `knowledge.cleared` 记入事件日志（用户身份），同一（事实，人物）以最后一次为准；服务端校验：只能对**已确认**的事实设置、人物必须在图上、章节必须在时间轴上。
- **采访与推演按它给信息**：提示词里“已知的事”= 默认推断 + 作者指定，指定不知道的一概不给。不含名词解释。

### 别名合并（带揭示时刻）

- 作者在人物详情里说明“『黑衣人』其实是 萧某”，并选读者得知于哪一章（也可以选“一直是同一人”）。**揭晓之前图上仍是两个人物，揭晓那一章起合成一个**：关系、状态、出处并到规范名下，首次出现取两者中更早的；别名与规范名之间的关系自动消失（不画自己指向自己）。可取消、可重设。
- **只由作者建立**，模型不会自行合并——认错人比不合并更糟（graph-design 里对别名消解的结论）。事实本身不被改动，合并是投影时的视图；别名按链解析并防环。
- 校验：两个名字都必须是图上真实出现过的人物；不能合并到自己；不能反过来绕成圈；已是别名的名字要先取消再重设；章节必须在时间轴上。
- 采访/推演：规范名人物能说出别名名下发生的事，提示词里告诉他“你在故事里还有这些称呼：黑衣人”；越界名单按原始名字算（揭晓前，别名若是后文才登场的人物，仍算越界）。

### 真实验证中暴露的问题（如实）

- 第一次跑 7 项里 1 项失败：我的测试问题写成“师父最近…”，周远不知道“师父”指沈砚，即使被指定知道也答“不知道”——是**测试措辞的问题**，已改成用名字提问。接着一次默认知道的用例失败：事实措辞是“暗中收下”，模型认为小满不会知道而装不知道——说明**默认推断对“秘密”类事实会过宽**（同章在场的身边人默认知道），需要作者用“设为他不知道”收窄；已把用例改成非秘密事实并连跑 3 次通过。这两次都不是产品代码的错，但说明模型对认知边是“守得住但不总是答得出”。

### M6.2d 局限（如实）

- 默认推断仍是启发式：同章在场的身边人的状态变化默认知道，**秘密、隐瞒、误会要作者逐条改**；没有“人物 A 以为 B 是好人”这类带错误信念的认知，只有“知道/不知道”。
- 认知边只作用于采访和推演的提示词，**不影响图上显示**（图仍是读者视角）；没有批量设置，事实很多时认知页签的列表会很长，没有筛选。
- 别名合并只能一对一选择，不会提示“这两个人可能是同一个人”（没有自动建议）；史官抽取时仍会把不同称呼记成不同人物，需要作者事后合并。
- 合并选择的是“读者得知”的章节；人物自己什么时候知道真身，要另外用认知边表达。
- 真实模型每组只跑几次，只用 flash。
