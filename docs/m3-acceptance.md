## 一、结论：未通过，但方向对、差距集中

**自动化全绿，真实模型回归不通过。** 对方报告里的命令我在干净安装后全部复现通过，但他们那边因为子进程没有继承 `DEEPSEEK_API_KEY`，把 M3 的真实回归**跳过了**；我这里有密钥，跑了：**`npm run test:m3:live` 在 300 秒后超时失败**。

更重要的是，我手动复现了失败的那一步，看清了产品实际的样子：

- ✅ **评审员真的抓出了预埋的矛盾**：真实 DeepSeek（`v4-pro/high`）读设定集和第三章后，发出 `challenge.raise`：“正文写‘裴照走进崇仁坊，右手按住刀柄’，与设定‘裴照是左撇子，惯用横刀’矛盾”。路由、任务图、每节点一次运行、费用预估都在工作。
- ❌ **界面看不到任何结果**：运行结束时线程卡 0、评审气泡 0；聊天里只有“评审 · 核验 / 工作流已完成”两行，评审员说了什么用户完全看不到。
- ❌ **强杀重开后**能看到评审气泡了，但**线程卡仍是 0**：质询卡无论实时还是重启后都不会渲染。
- ❌ **整个流程没有任何一步会升级成裁决卡**：只有一个评审节点，没人回复、没人复核；“最多两轮、未解决自动升级”只存在于纯函数与脚本化的 faux 单测里。

## 五、本次改动（P7–P10）

你报告的布局问题，我定位后一并修复：
- **根因**：任务行和提示条不在时间线的“28px + 内容”两栏网格里，竖线从中间穿过；圆点用的是文字符号 `●`，中心取决于字体。
- **修复**：两者改用同一网格，圆点改为 CSS 几何圆（中心必然落在竖线上，外圈遮住竖线），文字只在内容栏；占位气泡在工作流启动时清理；任务行显示“写手 · 撰写”；投影保存 `agentId / taskKind`，重启后同样显示。
- **回归防线**：`npm run test:layout` 新增几何断言——**每个圆点中心距竖线 ≤ 0.75px、文字不得压线**，并在演示数据里加入工作流场景。去掉修复时它报出“圆点偏离 5.0px、文字压线 −14px”，修复后通过。

## 六、下一步计划（约 6.5 个工作日）

核心思路：**先让用户看得见，再把质询回合真正编排起来，最后用真实模型验证。**

### 第 A 步：让工作流的结果看得见（1.5 天）— P1、P5

- 工作流节点运行在实时界面生成 Agent 气泡（带任务名、用量、工具步骤、输出文字），与重启后的投影一致。
- 会话用量汇总包含节点运行。
- **纸面显示当前章节**：监听 `file.updated`，读取并只读渲染对应章节（Markdown），写手写入后纸面立即出现；编辑功能仍在 M5。
- **验收**：faux 脚本化 `write-chapter`，断言：实时聊天里有写手与编辑两个气泡、纸面显示最终章节、会话用量非零；强杀重开后一致。

### 第 B 步：质询回合真正编排（2.5 天）— P2、P3、P4

- **渲染**：处理 `challenge.raise / reply / escalation.created`，实时与重启后都显示线程卡与裁决卡。
- **协调器驱动回合**：评审发起 `blocking` 质询 → 自动调度写手“回复”任务（接受并用 `doc.write` 修改，或反驳）→ 若反驳，调度评审“复核”任务（第 2 轮）→ 仍未解决则 `escalation.created`，工作流暂停等裁决；写手接受则线程关闭、返工落盘。
- **阻塞语义**：存在未解决的 `blocking` 质询时，工作流以“需要裁决”收尾，而不是 `succeeded`。
- 裁决选择（接受修改 / 保留原文）写成事件并驱动工作流继续。
- **验收**：faux 脚本化三条路径——①写手接受；②写手反驳一次后评审接受；③两轮仍分歧、升级裁决。每条都断言事件、线程卡、最终文件内容与重启恢复。

### 第 C 步：真实回归改成能说明问题的（1 天）— P6

- 断言：评审指出的质询正文包含“左 / 右”；线程卡出现；批准或裁决后章节文件被改写；
- 新增**无矛盾章节**的误报测试（评审不应发起 `blocking` 质询）；
- 覆盖 `all` 工作流；
- 升级路径用**脚本化的“固执写手”**（faux）保证确定，不依赖真实模型是否反驳；真实模型回归只验证“能抓出、可见、可裁决”。
- 纳入夜间回归（现在只有 M2 的）；M3 手动 workflow 保留。
- **验收**：真实回归通过；故意把评审提示词改坏时（不指出矛盾）它必须失败。

### 第 D 步：收尾与 M4 前置（0.5 天）

- 把 M3 的验收脚本与文档对齐；更新 `m3-progress.md`。
- 进入 M4 前：**默认模型恢复为写手 `v4-pro/high`、评审 `v4-pro/max`**（已定，我会提醒）。
