## 一、结论

**M3 的地基已经落地，但距离计划还有一半以上**：M3.0（结构整理与遗留项）基本完成；M3.1 的表与纯逻辑模块完成；M3.2–M3.8（工作流接入、质询、写入串行化、预算、群聊界面、集成回归）尚未进入产品链路。对方在 [m3-progress.md](m3-progress.md) 里如实列出了这些未完成项，这一点值得肯定。

## 三、缺陷与遗留项

| # | 严重度 | 事项 | 证据 |
|---|---|---|---|
| N1 | **高** | 重启后批准是“假批准”（仅保存密钥时） | 恢复路径写死 `apiKey: process.env.DEEPSEEK_API_KEY`，没有用保存的加密密钥。实测：用界面保存的密钥走到审批 → 强杀重开 → 点“批准”：卡片显示“已裁决：批准”，文件未写入，库里批准之后**没有任何事件**；只是运行项里多了一行红色“DeepSeek密钥未配置”。这正是 M2.1 修过的“假批准”，在这条路径上回来了。你发来的第二张截图就是这个状态 |
| N2 | 中 | 恢复的运行在界面上是隐形的 | 重启后批准，界面不进入“运行中”（没有停止按钮），期间可以并发发消息；也是真实回归 E2 失败的原因（脚本在运行结束前就检查文件，属竞态） |
| N3 | 中 | 审批卡预览不换行，横向撑破卡片 | **你报告的问题，已修复**：预览是 `<pre>`，没有任何样式；现在自动折行、长路径断开、卡片内部滚动。新增 `npm run test:layout`（最窄与常规窗口 × 亮暗色，检查聊天区无横向溢出），去掉修复时它报出 589–660px 溢出，已纳入 CI |
| N4 | 中 | “章节定稿后自动评审”是摆设 | 开关无行为；而“定稿”这个动作目前也不存在 |
| N5 | 中 | M3 的主体功能未接入 | 见上表；这部分是下一步的主线 |
| N6 | 中 | `executor.ts` 1168 行 | 往里再加任务调度与质询会失控，需要先按职责拆分 |
| N7 | 低 | 预算默认无限，项目预算未持久化 | 多 Agent 费用没有任何保护 |
| N8 | 低 | 夜间回归在未配置密钥的仓库里每晚显红 | 需要你在仓库 Secrets 添加 `DEEPSEEK_API_KEY`，或暂时停用该工作流 |

### 实测确认没问题的部分

faux 单测覆盖了运行经过任务事件与终态、fallback、审批快照重启后继续（对方自述；我复现了测试通过）；审批预览、权限提示、重启批准（环境变量密钥）的真实链路；CI 全绿。

## 五、下一步计划（约 10 个工作日）

顺序是：**先补信任，再接功能**。第 0 步让已有功能可信，之后才往上叠任务图与质询。

### 第 0 步：恢复路径与可信度（1.5 天）

| 事项 | 对应 | 验收 |
|---|---|---|
| 恢复与续跑改用凭据存储的密钥（通过运行请求或凭据提供器传入），不再读环境变量 | N1 | 新增真实回归场景 E′：**应用环境不带密钥、只靠界面保存**，强杀重开后批准，文件落盘、运行收尾 |
| 渲染端“先等后台确认，再标记已裁决”；恢复失败要显示原因并保持卡片可再次操作；后台任何失败都要落成 `run.error` 事件 | N1 | faux 测试：恢复失败时卡片不被标为已裁决 |
| 恢复的运行进入“运行中”：显示停止按钮、禁止并发发送、可中止 | N2 | 脚本改为等待 `run.finished` 事件，不再靠按钮消失 |
| 删除或隐藏“自动评审”开关，直到“定稿”真正存在 | N4 | 设置页不再出现无效控件 |
| `executor.ts` 按职责拆分：审批与快照、fallback、工具装配、事件映射、运行主循环 | N6 | 每个模块 < 300 行，现有 faux 测试与 20/20 保持通过 |
| 预算：恢复为默认单次 0.05 美元并可改（见文末“需要你定”） | N7 | 超出时暂停并请求确认 |

### 第 1 步：工作流接入运行（2 天）

- 用户消息 → 路由 → 创建工作流实例 → 每个节点一个任务行、一次 Agent 运行；任务状态由事件投影。
- 首批：`write-chapter`（写手 → 编辑）、`review-only`。
- 运行前对整个工作流给出预估费用，全流程需确认。
- **验收**：faux 脚本化的 `write-chapter` 端到端：任务顺序、产物传递、终态、每个任务的用量。

### 第 2 步：质询协议贯通（2 天）

- 协调器计数每个线程的轮次，第 3 轮前强制升级；`blocking` 质询未解决时，下游任务不得成功。
- 渲染端处理 `challenge.*` / `escalation` 事件并支持重启恢复：质询线程卡、裁决卡成为真实数据。
- 裁决选择写成事件，驱动工作流继续或返工。
- **样例项目《长安夜》**：`examples/长安夜/`（章节、含“裴照是左撇子”的设定集、一处预埋矛盾）。这些设定是我随手编的虚构内容，不当作你的创作；要扩写前我会先问你。
- **验收**：faux 脚本化“评审质询 → 写手反驳 → 评审维持 → 升级裁决”，事件、线程卡、裁决后续调度一致。

### 第 3 步：写入串行化（1 天）

- 按产物加锁，启动时记录 `parentRevision`，提交时若已变化则基于最新版本重试一次，仍冲突则降级为提案。
- **验收**：faux 让两个 Agent 同时写同一章，不丢任何一方内容。

### 第 4 步：群聊界面（1.5 天）

- 任务进度时间线、并行任务泳道、预估费用卡、“继续被中断的运行”“请评审”按钮、会话用量汇总。
- 整条流程的 Playwright 驱动与截图入 [design/](design/README.md)；布局检查（`test:layout`）覆盖新增卡片。

### 第 5 步：真实模型集成回归（1.5 天）

- 真实 DeepSeek：写第三章（写手 → 编辑）→ 请评审 → 评审应找出《长安夜》里预埋的矛盾 → 质询线程 → 裁决 → 返工。
- 同时放入一章**无矛盾**文本，测评审的误报率。
- 纳入夜间回归；记录预估费用与实际费用的偏差。
