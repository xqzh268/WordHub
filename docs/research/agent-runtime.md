# WordHub Agent运行底座与多Agent编排调研\n\n> **勘误（2026-10-03）**：本文部分结论已被后续调研修正，请先阅读 [README.md](README.md) §二“对早期三份文档的审阅”。\n\n**核查日期：2026-10-03（Asia/Shanghai）**\n**范围：**仅核查第一方仓库/官方文档；结论用于Windows桌面端Electron+Node独立worker的首版技术规划。第三方博客、Benchmark和未运行的样例不作为能力证明。\n\n## 结论摘要\n\n首版建议采用“**Electron UI + Node编排worker + 持久事件日志/项目库 + Pi agent-core/pi-ai执行层**”的分层方案：\n\n1. Pi的`@earendil-works/pi-agent-core`提供单Agent状态、工具调用、流式事件、队列、steering/follow-up、并行或串行工具执行；`pi-ai`提供多模型供应商、统一流式接口、工具参数校验、token/cost统计。两者适合作为Agent执行内核，不等于WordHub的项目、文档、引用库或多Agent协作产品。\n2. Pi coding-agent的TypeScript SDK可嵌入Node/Bun；RPC模式可启动长驻子进程，以JSONL命令/响应/事件隔离进程。Windows Electron建议首版以**独立Node worker进程或RPC子进程**运行每个Agent/任务，UI只订阅事件；API key、文件写入和工具权限留在worker。\n3. Pi官方新增`@earendil-works/pi-durable`，提供持久会话、原子commit、任务检查点、恢复、fork/subagent和task graph等概念，但README明确`Experimental`且API可能无预告变化。可做验证性试验或后续替换点，首版项目级数据模型/事件日志仍应由WordHub自建，避免把实验包的内部存储契约当稳定产品边界。\n4. LangGraph JS是更完整的图编排运行时：官方定位为低层、有状态、长运行Agent orchestration，内置durable execution、streaming、human-in-the-loop和持久化。其checkpointer适合thread短期状态，store适合跨thread长期共享知识；`interrupt()`可暂停并持久化状态，等待用户确认后按`thread_id`恢复。若WordHub优先要可视化DAG、暂停/恢复和复杂分支，可在Node worker中评估LangGraph；若优先轻量、桌面本地和Agent自定义，Pi内核+自建编排器更小、更可控。\n5. 不建议首版自由群聊作为默认调度。采用**中央协调器 + 声明式DAG + 有界协商回合**：协调器分发纲领/写手/编辑/评审/观察者任务，Agent之间通过带schema的消息和事件日志通信；只在评审发现冲突时开启最多N轮定向质询，超时或循环则转人工确认。这样保留“像工作群聊”的可见体验，同时让结果可恢复、可审计、可测试。\n\n## Pi底座核查\n\n### `pi-ai`：模型与传输层\n\n官方README将`@earendil-works/pi-ai`定义为统一多供应商LLM API，含自动认证解析、token/cost跟踪，以及跨模型上下文交接；目录列出OpenAI、Anthropic、Google、DeepSeek、Mistral、OpenRouter、Ollama/vLLM/LM Studio等兼容接口。`Models`集合按provider路由请求，`stream()`会发出文本、思考、工具调用、完成和错误事件；工具参数用TypeBox校验，可读出输入/输出token与成本。\n\n**WordHub可复用：**模型注册、流式事件映射、模型/推理强度配置、成本和token遥测。\n**WordHub必须自建：**项目/用户级密钥安全、引用与文档权限、模型降级策略、敏感内容脱敏、配额和审计策略。Pi的provider支持不代表WordHub已完成这些产品政策。\n\n来源：[`pi-ai`官方README](https://github.com/earendil-works/pi/blob/main/packages/ai/README.md)（可复现原文：[raw](https://raw.githubusercontent.com/earendil-works/pi/main/packages/ai/README.md)）。\n\n### `pi-agent-core`：单Agent执行循环\n\n官方README显示`Agent`是有状态Agent，支持工具执行和事件流。它定义`AgentMessage`（可通过声明合并加入应用自定义消息），在每次模型调用前可`transformContext`/`prepareRequest`，并通过`subscribe`观察`agent_start`、`turn_start`、`message_update`、`tool_execution_*`、`turn_end`和`agent_end`。工具默认可并行执行，也可全局或单工具设为串行；`beforeToolCall`能阻止调用，`afterToolCall`能改写结果或终止后续请求。`steer()`用于当前运行中的定向输入，`followUp()`用于运行结束后的排队输入；`abort()`和`waitForIdle()`提供控制。\n\n这足以支撑“写手/编辑/评审各自一个Agent运行时”和实时工作流展示，但它只解决**单个运行时**：多Agent身份、消息路由、共享项目记忆、文档版本、DAG、冲突解决、人审策略和跨进程调度均需WordHub建立。\n\n来源：[`pi-agent-core`官方README](https://github.com/earendil-works/pi/blob/main/packages/agent/README.md)（[raw](https://raw.githubusercontent.com/earendil-works/pi/main/packages/agent/README.md)）。\n\n### Pi coding-agent SDK、RPC与扩展\n\n官方SDK文档说明：`@earendil-works/pi-coding-agent`可嵌入Node.js/Bun，`createAgentSession()`提供会话、模型、工具和资源；会话默认持久化，`SessionManager`负责JSONL entry树、活动分支、分支/fork、恢复和上下文压缩；`cwd`决定工作区资源发现和内置工具路径。SDK可注入`sessionManager`、`resourceLoader`、工具、模型等边界。\n\nRPC文档说明：`pi --mode rpc`以长驻子进程运行，stdin/stdout使用严格JSONL命令、响应和事件；每个命令可带`id`，客户端按ID关联异步响应，事件持续流式输出。RPC适合语言无关集成、进程隔离、IDE和自定义UI；官方建议同进程Node/Bun优先SDK，隔离或跨语言优先RPC。对于Windows Electron，Node主进程可作为编排器，独立worker通过IPC/JSONL承载Agent运行，避免渲染器直接接触凭证和文件工具。\n\n官方扩展文档提供`registerTool`、`registerCommand`、生命周期钩子、自定义provider、MCP、事件总线和`appendEntry`等扩展点，但明确扩展与Pi进程拥有相同操作系统权限，可读取提示、工具调用、文件、凭证和会话历史；因此用户自定义Agent扩展必须做签名/信任、能力声明、目录白名单和确认弹窗。\n\n来源：[`SDK`](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)、[`RPC`](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc.md)、[`扩展`](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md)、[`coding-agent README`](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/README.md)。\n\n### `pi-durable`（实验性分支）\n\n官方README将其定义为durable agent harness：对话、模型轮次、工具调用和自有状态在展示前提交到存储；进程崩溃后重新打开可继续。`Harness`管理Storage和任务调度；Conversation是不可变transcript；Commit可原子追加entry、修改文档和创建任务；Task在每一步保存checkpoint；支持SQLite/JSONL存储、`resume()`、相同`requestId`幂等提交、fork、子任务和task graph。它还提供按Conversation配置模型/工具/扩展/cwd，以及`viewState()`给UI读取结构化状态。\n\n这些原语很贴近WordHub的多session、恢复和项目共享记忆，但**README第一行标明Experimental且API可无通知变化**。首版可建立适配器接口（`AgentRuntimeAdapter`、`ConversationStore`、`TaskScheduler`），并用真实Windows崩溃/重启试验决定是否采用；在验证前不把`pi-durable`的存储格式直接暴露为WordHub持久化协议。\n\n来源：[`pi-durable`官方README](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md)（[raw](https://raw.githubusercontent.com/earendil-works/pi/main/packages/durable/README.md)）。\n\n### LangGraph JS与轻量方案对比\n\nLangGraph官方将其定位为低层编排框架/运行时，允许在同一张图中混合确定性步骤和LLM步骤，并提供durable execution、streaming、人工介入和memory。持久化由两层组成：checkpointer保存单thread图状态快照（对话连续、人工介入、time travel、容错），store保存跨thread应用知识（项目共享记忆、用户偏好等）。`interrupt()`在节点任意位置暂停，checkpointer保存精确位置，使用同一`thread_id`和`Command({resume})`继续；并行分支可同时产生多个interrupt，恢复时应按interrupt ID映射回答。\n\n| 方案 | 已有强项 | WordHub仍需自建/关注 ↓\n纲领Agent（澄清问题，输出Outline/验收标准）\n      ↓\n写手Agent（按part生成候选稿） ──┐\n      ↓                         ├→ 编辑Agent（语言/格式/引用）\n观察者Agent（人物/概念图谱） ───┘\n      ↓\n评审Agent（幻觉、偏纲领、证据缺口）\n      ↓\n协调器：通过 / 定向返工 / 请求人类确认\n```\n\n建议每个Task输入输出均为JSON Schema对象，至少包含`task_id`、`project_id`、`session_id`、`parent_revision`、`context_refs`、`artifacts`、`claims`、`questions`、`status`。正文和文档修改以不可变revision提交；只有协调器能把候选revision提升为当前版本，防止并发Agent直接覆盖文件。\n\nAgent质询使用`Question`事件（目标Agent、问题、依据引用、截止时间、最大回合数），回答使用`Answer`事件；默认最多2轮、总时限可配置，超过即标记`needs_human`。群聊UI展示事件和摘要，但不要让UI中的消息顺序成为唯一事实来源；事件日志才是恢复、审计和重放依据。\n\n### 为什么不默认自由群聊\n\n自由群聊适合探索，但会出现重复调用、循环争论、上下文泄漏、不可预测成本、无法确定最终稿来源以及并发写入冲突。中央调度把“谁在何时基于哪个revision做了什么”固定下来；局部质询仍可保留专家协作感。可在高级模式允许用户手动发起群聊，但群聊产物必须回到带schema的Task/Revision流程。\n\n### 冻结上下文、并发写入和人工确认\n\n* **冻结上下文：**Task开始时记录`context_snapshot_id`，包含纲领revision、选定参考片段/页码、项目记忆版本和Agent配置。后续输入只能追加新引用，不能静默改变已执行任务的依据。\n* **并发写入：**文档采用revision或区块级锁；Agent先生成patch/diff，协调器检查`parent_revision`，冲突时重新基于最新revision生成。参考库、图谱和记忆使用带来源的upsert，保留冲突值而不是最后写入覆盖。\n* **人类确认：**纲领定稿、外部文件写入、引用加入正文、评审否决、冲突超过阈值和高风险工具调用触发`approval_required`。UI显示差异、证据和影响，用户批准/拒绝事件写入同一日志。可借鉴LangGraph interrupt语义，但WordHub需定义自己的审批schema和权限。\n* **事件日志：**事件采用append-only JSONL/SQLite表，保存输入、Agent版本、模型、提示摘要、工具调用、引用、token/cost、输出revision、错误、审批和重试；事件ID全局唯一、任务提交使用幂等key。日志是UI流、恢复和导出审计的共同来源。\n\n## Windows Electron落地建议与里程碑门槛\n\n1. **运行时Spike（门槛：可恢复）**：Node worker启动一个Pi Agent，流式回传事件；验证Windows路径、中文文件名、取消、超时、异常退出、重启恢复。并行比较SDK内嵌与RPC子进程，记录启动延迟、内存和事件丢失。\n2. **协调器最小闭环（门槛：可重放）**：实现纲领→写手→编辑→评审DAG；事件日志可从任意Task checkpoint恢复；只允许协调器提交文档revision；模拟评审返工和两轮质询。\n3. **项目/session/共享记忆（门槛：隔离）**：项目绑定本地目录；多个session共享项目记忆但互不串线；引用片段带来源位置；导入/导出后可重建图和会话。\n4. **人审与权限（门槛：可控）**：审批事件、取消/重试、工具目录白名单、外部写入确认、API key不进渲染器和日志；扩展Agent显示能力声明并默认最小权限。\n5. **双场景验收（门槛：真实任务）**：科研任务验证引用、证据和参考文献格式；小说任务验证人物/概念图谱、章节一致性和文风参考。记录每个Agent的完成率、幻觉/偏纲领缺陷、平均/95分位延迟、token/cost、超时和人工介入率。\n\n## 未验证事项与风险\n\n* 尚未在本机安装或运行Pi最新包，Windows Node版本、RPC子进程退出码、路径编码和真实token成本需Spike实测。\n* `pi-durable`当前为Experimental；其SQLite/JSONL模式、task graph、fork和resume虽有官方示例，尚未证明在WordHub的并发写入、Electron重启和升级迁移下满足产品要求。\n* LangGraph官方文档描述了持久化和interrupt语义，但本报告未验证其Windows桌面打包、SQLite并发和离线模型接入；需同一任务基准与Pi方案对照运行。\n* Pi扩展与进程同权限；在没有沙箱/白名单前，不应允许用户随意安装第三方扩展或让Agent直接写任意路径。\n* “观察者”科研版关系图谱建议先做**概念—主张—证据—方法—数据—结论**图：节点保留来源页码/段落和置信度，边区分支持、反驳、依赖和待验证；这只是产品设想，需通过真实论文任务验证检索和抽取质量。\n\n## 参考来源（第一方）\n\n* Pi mono：<https://github.com/earendil-works/pi>\n* Pi
